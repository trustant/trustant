# End-to-End Tests

End-to-end tests live under `tests/` and are opt-in. They are not part of
`go test ./...` because they interact with a live Trustable/Nuvolaris cluster,
may create app users, launch OpenCode/Vite, and drive a browser.

Generated benchmark reports, traces, and logs belong under `benchmark-results/`
and are local artifacts. They must be ignored by git and not committed.

## Multi-provider application benchmarks

The same guarded Stack application scenario is exposed through three provider
entrypoints:

```bash
TRUSTABLE_E2E_MODEL=qwen3.6:35b ./tests/e2e_bestia_app.sh
TRUSTABLE_E2E_MODEL=qwen3.5:cloud ./tests/e2e_ollama_cloud_app.sh
TRUSTABLE_E2E_MODEL=qwen3.6-27b ./tests/e2e_regolo_app.sh
```

The entrypoints must share the implementation in
`tests/e2e_provider_common.sh`; provider-specific scripts only select the
profile. Each run temporarily updates the global Trustable test workspace
configuration, launches the existing guarded action-workflow runner, and
restores the exact original configuration on success, failure, or signal. A
local lock rejects concurrent provider benchmarks because they share that
configuration.

Test inputs may be exported in the shell or placed in `.env.e2e` at the repo
root. An alternate file is selected with `TRUSTABLE_E2E_ENV_FILE`. Both names
are covered by the repository `.env*` ignore rule. The env file is sourced as a
trusted local shell file and should have mode `0600`. Required values missing
from an interactive terminal are requested without echo for secrets. A CI or
other non-interactive run must fail with the missing variable name instead of
hanging for input.

Provider inputs are:

| Entry point | Provider profile | Required input | Default base URL |
| --- | --- | --- | --- |
| `e2e_bestia_app.sh` | `bestia` | `TRUSTABLE_E2E_MODEL` | `http://bestia:11434/v1` |
| `e2e_ollama_cloud_app.sh` | `ollama` | `TRUSTABLE_E2E_MODEL`, `TRUSTABLE_E2E_OLLAMA_API_KEY` (or `OLLAMA_API_KEY`) | `http://localhost:11434/v1` |
| `e2e_regolo_app.sh` | `trustable` | `TRUSTABLE_E2E_MODEL`, `TRUSTABLE_E2E_API_KEY` (or `API_KEY`) | `https://api.nuvolaris.io/v1` |

`TRUSTABLE_E2E_BASE_URL` overrides a default. The Ollama Cloud mode deliberately
uses the Ollama server inside the Trustable pod; the selected model must be a
cloud-capable model available to that server. The Regolo mode uses the
OpenAI-compatible inference endpoint through `api.nuvolaris.io`.

BestIA benchmark inference does not require an E2E API-key input. Its temporary
profile must remove `api_key`, even when the prior provider left one in the
workspace configuration; it must not preserve that value or invent a dummy
credential. Ollama Cloud and Regolo credentials are written only to their
temporary global provider configurations needed to generate OpenCode's managed
provider block. Credentials must never be added to a generated application's
`.env`, `.env.production`, or app env map. The temporary host backup has mode
`0600` and is deleted after a successful restore. Benchmark logs and reports
must not include credential values.

Before launching the action workflow, the common runner reads the temporary
configuration back from the pod and fails preflight unless the effective
provider identity, base URL, default/small model, model limits, and credential
presence match the selected profile. The preflight also captures the effective
saved Headroom state, using disabled, `proxy`, and port `8787` when the
corresponding configuration fields are absent.

The default prompt is deliberately non-technical. It asks for a visible page
that performs real write/read verification for Redis, MongoDB, PostgreSQL, and
S3. The common wrapper enables the existing OpenServerless action mutation,
deploy, setup, completion, tool-safety, and changed-worktree assertions. A
caller can select an existing disposable app with `TRUSTABLE_E2E_APP` or a
template with `TRUSTABLE_E2E_REPO`; otherwise `trustable-ai/trureact` is used.

Every run creates:

```text
benchmark-results/<UTC>-<provider-mode>-<model>/
  report.json
  run.log
  playwright/
```

`report.json` uses schema `trustable-e2e-benchmark/v1` and records provider
mode, generated OpenCode provider key, model, base URL, UTC start/end,
wall-clock duration, exit code, outcome, target app/template, artifact paths,
and normalized check names. It includes the verified effective configuration
with only credential-required/configured booleans, never the credential value,
plus an explicit Headroom object and `headroom` check whose result is `enabled`
or `disabled`. The same object is appended to
`benchmark-results/index.jsonl` for structured processing. A compact table is
appended to `benchmark-results/summary.tsv` for direct comparison between
models and providers. Playwright traces, screenshots, and videos are retained
under the run's `playwright/` directory according to the base runner policy. See
[provider-e2e-flow.svg](provider-e2e-flow.svg).

## Issue 98 guardrail test

`tests/e2e_issue98.sh` runs the Playwright spec
`tests/issue98.spec.mjs`.

The test must use browser-visible FQDN hosts for browser/API requests:

- `trustable.<domain>` for Trustable UI and `/api/*`;
- `opencode.<domain>` for browser-visible OpenCode requests;
- `vite.<domain>` for browser-visible app checks after launch/deploy.

Pod-local checks must stay explicit:

- `kubectl exec trustable-0 -c trustable -- ...` for reading app workbench files
  and running `check_openserverless_actions.sh`;
- `http://localhost:5173` only from inside the Trustable pod, where
  `ops ide devel` runs.

The script detects `<domain>` from `trustable-ing`, then from the Nuvolaris
apihost annotation, and finally falls back to `miniops.me`. Callers may override
this with `TRUSTABLE_E2E_DOMAIN`.

The test can run in two modes:

- Existing app mode: `TRUSTABLE_E2E_APP=<name> ./tests/e2e_issue98.sh`.
- Fresh app mode:
  `TRUSTABLE_E2E_REPO=<org/repo> [TRUSTABLE_E2E_PASSWORD=<password>] ./tests/e2e_issue98.sh`.

Fresh app mode may delete the created app at the end. Set
`TRUSTABLE_E2E_KEEP_APP=1` to preserve it for debugging.

The issue 98 runner must always call `DELETE /api/launch` at the end to stop
the OpenCode and Vite processes it started. In existing app mode it must not
delete the app repository.

The issue 98 E2E must verify at least:

1. Trustable UI loads through `trustable.<domain>`.
2. `/api/launch/<app>` succeeds and returns `encdir`, `b64dir`, `left=4096`,
   and `right=5173`.
3. `opencode.<domain>/project` exposes only the launched app and its canonical
   workbench path.
4. `opencode.<domain>/session?directory=<encdir>&roots=true&limit=10` lists a
   session for the canonical workbench path.
5. A second root session created through OpenCode appears together with the
   launch session in `/api/opencode/sessions/<app>`, and the `app.html`
   Sessions pulldown renders and selects it.
6. `opencode.<domain>/mcp` includes `openserverless` and the bounded `browser`
   MCP server.
7. `<workbench>/<app>/AGENTS.md` exists and contains the Trustable-managed
   block that explicitly demotes `CLAUDE.md` and other legacy/template agent
   files from mandatory Trustable instructions.
8. `<workbench>/<app>/opencode.json` contains:
   - instructions pointing first to `.openserverless-contract.md`, then
     `opencode.md`; the test should compare their `realpath` values with the
     canonical workbench path because `/home/trustable/workbench` may be a
     stable symlink into `/home/trustable/workspace/workbench`;
   - `mcp.openserverless.command == ["openserverless-mcp"]`;
   - `mcp.browser.command == ["trustable-browser-mcp"]`, with the derived
     Vite origin and the app-scoped artifact directory;
   - permission denies for `packages/**/__main__.py`, `packages/**/*.zip`,
     `ops action`, and `ops action *`.
9. `timeout 60 check_openserverless_actions.sh .` passes inside the app
   workbench.
10. The pod-local dev server responds at `http://localhost:5173` from inside the
   Trustable pod.
11. `vite.<domain>` responds after launch/deploy.

Unit coverage must also prove that manual ZIP writes are rejected, normal
sibling deploy archives are accepted, stale or missing archives require
deploy, and setup/completion remain blocked until deploy succeeds.

The runner also includes an opt-in second layer for model behavior. It is
disabled by default because it can consume tokens, depends on the selected
model/provider, and may take several minutes.

Set `TRUSTABLE_E2E_RUN_PROMPT=1` to enable the prompt-driven test. The test must:

1. launch or create the target app using the same app-selection rules as the
   fast guardrail test;
2. send `TRUSTABLE_E2E_PROMPT` to
   `opencode.<domain>/session/<id>/prompt_async`, or a read-only default prompt
   that asks OpenCode to run `timeout 60 check_openserverless_actions.sh .`;
3. poll OpenCode session messages and status until the new prompt has produced
   assistant text and no tool remains running;
4. fail on pending OpenCode questions;
5. fail on pending permissions unless `TRUSTABLE_E2E_AUTO_APPROVE=1` is set, in
   which case each permission may be replied with `once`;
6. inspect only the messages created by the current prompt, so historical
   session messages cannot create false positives;
7. require at least one tool call unless `TRUSTABLE_E2E_PROMPT_EXPECT_TOOLS=0`
   is set;
8. fail on tool errors unless `TRUSTABLE_E2E_PROMPT_ALLOW_TOOL_ERRORS=1` is set.
   The only built-in exception is a `list` tool `ENOENT` for a missing directory
   inside the app workbench, for example optional folders such as
   `packages/setup`; those probes are exploration noise and must not hide edit,
   deploy, action, shell, MCP, or checker errors;
9. fail when a shell tool uses raw `ops action` or `ops action *`;
10. optionally require OpenServerless action MCP usage when
    `TRUSTABLE_E2E_EXPECT_OPENSERVERLESS_TOOL=1` is set;
11. rerun `check_openserverless_actions.sh .` after the prompt;
12. optionally require a changed worktree when
    `TRUSTABLE_E2E_PROMPT_EXPECT_CHANGES=1` is set.

The prompt layer should normally be run with a targeted grep:

```bash
TRUSTABLE_E2E_RUN_PROMPT=1 \
TRUSTABLE_E2E_APP=<app> \
./tests/e2e_issue98.sh --grep 'OpenCode prompt'
```

See [issue98-e2e-flow.svg](issue98-e2e-flow.svg) for the test flow.

### Model-driven action workflow

`tests/e2e_action_workflow.sh` creates a temporary app by default and submits a
non-technical request that requires both a backend action and initial setup.
The test reads the actual OpenCode tool trace and fails unless:

1. at least one OpenServerless action mutation occurs;
2. no action ZIP is created or changed manually;
3. every action mutation has a later `ops ide deploy`;
4. the final action mutation is followed by deploy, then `ops ide setup`;
5. `trustable_completion_check` runs after deploy and setup;
6. the aggregate app checker passes and the worktree contains the requested
   changes.

For setup ordering, the relevant deployment is the first successful deploy
after the final action mutation. A later frontend-only `ops ide deploy` does not
make setup stale and must not require another `ops ide setup`.

A browser locator or navigation error is tolerated only when a later call to
the same browser tool succeeds in the same prompt. Unrecovered browser errors
and every action, deploy, setup, checker, MCP, or shell error still fail the
test.
This recovery rule includes strict-locator ambiguity and out-of-range index
errors: the later successful interaction is evidence that OpenCode consumed
the diagnostic and selected a valid locator.

The trace inspection must reject raw `ops action` and `wsk action` commands,
including commands prefixed by `timeout`, `env`, inline variables, or `sudo`.
It must also reject `ops ide login`: Trustable already performed login before
starting the managed OpenCode and Vite processes.

A stale replacement edit is tolerated only when OpenCode follows the mandatory
recovery sequence in the same prompt: re-read the same file, then successfully
edit or rewrite that file. An unrecovered stale edit remains a failure.
If the reread proves that the requested `newString` is already present and the
failed `oldString` is absent, the edit is also considered recovered; requiring
another no-op write in that case would add noise rather than evidence.
An invalid edit call missing replacement arguments is likewise considered
recovered only when a later edit or full write of that same file succeeds.

A mutation denied because compaction started is tolerated only when a later
`trustable_context_recover` succeeds. A guessed missing file is tolerated only
when OpenCode inspects its parent and reads the actual sibling module. These
exceptions preserve evidence of correct recovery rather than suppressing tool
failures generally.

A critical command rejected by the masking guard is considered recovered only
when OpenCode later runs the corresponding build/check/deploy/setup command
without a masking pipeline and that direct command completes successfully. A
masked command that reaches execution, or a rejected attempt without a later
successful direct check, remains a failure.

The runner accepts `TRUSTABLE_E2E_APP` for a disposable existing app, otherwise
uses `TRUSTABLE_E2E_REPO=trustable-ai/trureact` and deletes the generated app at
the end. See
[issue98-action-workflow-e2e.svg](issue98-action-workflow-e2e.svg).

Fresh-user provisioning may briefly return `ops ide deploy failed: Repeat the
login` even though the immediately preceding login succeeded. The E2E launch
helper retries that exact transient response up to three times with bounded
backoff. Every other launch failure remains immediate and fatal.

### Long session and compaction recovery

`tests/e2e_compaction.sh` creates a temporary app, establishes a real OpenCode
conversation, calls the OpenCode compact-session API, and continues work in the
same session. It must prove that:

1. a real compaction part is stored in session history;
2. `trustable_context_recover` completes before the first successful
   post-compaction mutation; a mutation attempt rejected by the recovery gate
   is valid enforcement evidence and is not treated as an executed mutation;
3. the continued change reaches `trustable_completion_check` and the aggregate
   checker passes;
4. stopping and relaunching the app reuses the same session ID;
5. messages containing the pre/post-compaction marker remain readable after
   relaunch.

See [issue98-compaction-e2e.svg](issue98-compaction-e2e.svg).

The test first uses `/api/session/<id>/compact`. OpenCode releases that expose
the route but return `503 Session compact is not available yet` are exercised
through the stable `/session/<id>/summarize` endpoint with the generated
provider/model reference. Both paths must produce the same real compaction
event and recovery proof; no synthetic plugin event is accepted.

### Authentication flow

`tests/e2e_auth.sh` extends the prompt-driven Issue98 test with the missing
browser authentication contract. It uses a non-technical prompt asking for
account creation, login, a private area, persistence after reload, and logout.
The prompt and browser assertions must run on the same temporary app before
cleanup; creating one app for the prompt and another for browser assertions is
not valid. The OpenCode trace must also satisfy the guarded action workflow,
including OpenServerless MCP, deploy, setup, and completion. After OpenCode
finishes, Playwright must:

1. open the browser-visible app host;
2. reach both login and registration from the public home page;
3. create a unique account through the rendered form;
4. enter the protected area from successful registration without a second
   manual login;
5. reload the whole page and remain authenticated;
6. log out and confirm that the public login control returns;
7. log in again with the account created by the test and survive another
   reload.

Before app creation, the runner waits up to 60 seconds for the browser-visible
Trustable server to return a successful response. This covers the short ingress
readiness interval after a pod rollout without retrying application creation or
hiding API errors once Trustable is reachable.

The prompt waiter accepts technical completion only after a completed assistant
message has a finish reason other than `tool-calls`. User prompt text, reasoning
text, and a temporary idle state after an MCP/tool result cannot end the
model-driven phase. The prompt assertion then separately requires non-empty
final assistant text, so a model that stops inside private reasoning fails
immediately instead of waiting until the global timeout.

The test records the standard Playwright trace, screenshot, and video on
failure. It intentionally validates behavior rather than assuming hash routes,
specific React components, or a fixed visual design. Set
`TRUSTABLE_E2E_AUTH=1` to include this test, or run `npm run e2e:auth` for the
model prompt plus browser flow.

For a retained app whose model phase completed but whose runner assertion
failed afterwards, set `TRUSTABLE_E2E_RUN_PROMPT=0` and
`TRUSTABLE_E2E_VALIDATE_EXISTING_PROMPT=1`. The resumed test rereads the durable
OpenCode session and reapplies tool safety, final-response, action ordering,
deploy/setup/completion, checker, and changed-worktree assertions before it
runs the browser flow. Resume must never bypass validation of the model trace.

See [issue98-auth-e2e.svg](issue98-auth-e2e.svg).

The session-enforcement architecture is documented in
[issue98-session-enforcement-flow.svg](issue98-session-enforcement-flow.svg).

## Issue 99 MongoDB capability guardrail

Issue 99 extends the prompt-driven E2E layer for the Stack Nuvolaris prompt:

```text
Vorrei una sezione o pagina "Stack Nuvolaris" nella home dell'app.
Deve verificare in modo visibile lettura e scrittura dei componenti dello stack:
Redis, MongoDB, Postgres e S3.
```

MongoDB must be treated as a first-class document database capability, separate
from Milvus/vector search.

The fast launch/config checks must verify:

1. `openserverless` is always present in generated `opencode.json`.
2. Service MCP servers are generated only from the official post-login
   `~/.ops/config.json` capability blocks.
3. `mcp.mongodb` is present only when `~/.ops/config.json` exposes official
   MongoDB capability, for example a `mongodb` block with a resolvable
   connection string or a login-derived `MONGODB_URI`.
4. A casual workbench `.env` variable must not enable MongoDB MCP by itself.
5. `.mcp.json` contains the same MongoDB server only when `opencode.json` does.

The prompt-driven check must fail explicitly when:

1. OpenCode creates a pending/running `question` tool or pending question API
   entry asking the user how to configure MongoDB or which infrastructure choice
   to make.
2. Any new prompt message, tool input, or generated file maps MongoDB to
   Milvus, `MILVUS_*`, `pymilvus`, `MilvusClient`, or `milvus_cli`.
3. Any generated action source treats `MDB_MCP_CONNECTION_STRING`, `MONGODB_URI`,
   `MONGO_URL`, `MONGO_CONNECTION_STRING`, or `MDB_CONNECTION_STRING` as an app
   runtime env var without a generated MongoDB action/runtime binding.
4. The generated app marks MongoDB success without a real configured MongoDB
   read/write path. When official MongoDB capability is present, the app `.env`
   must not expose `MONGODB_URI`; the action wrapper must include the generated
   `init_mongodb` binding, and the Stack check must write/read the expected
   value through `ctx.MONGODB` or `ctx.MONGODB_CLIENT`.
5. The prompt step relies on S3 MCP bucket listing as the proof for app S3
   behavior instead of validating the `action-add-s3`/action path or configured
   user buckets. The Trustable runtime wrapper for `mcp-s3` should also prevent
   known-invalid bucket-listing tools from surfacing to OpenCode.

Expected behavior:

- If MongoDB is configured, the app writes and reads the requested nonce/value
  from MongoDB and shows the real read value.
- If MongoDB is not configured, the app shows `non configurato` or an explicit
  error for MongoDB, records that in README, and continues to validate the other
  configured stack services.
- The agent must not ask the user technical MongoDB provisioning questions.
- The agent must not use Milvus as a MongoDB substitute.
- Service MCP success is diagnostic only and must not be treated as proof of an
  action runtime binding.
